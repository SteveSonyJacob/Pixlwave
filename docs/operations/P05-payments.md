# P05 sandbox operations and validation

Updated 2026-09-25. No sandbox credentials or live provider acceptance were available in this workspace session.

1. Use a non-production Supabase/PostgreSQL environment in India. First point `DATABASE_URL` at an isolated database whose name contains `pixlwave_test` and run `npm run db:test`; this destructive command refuses other names. Then apply `npm run db:migrate` to the integration environment. Do not run `db:test` against a shared database.
2. Set `APP_ENV=staging` or `test`, `PAYMENT_PROVIDER=razorpay`, and server-only `RAZORPAY_KEY_ID` (`rzp_test_...`), `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRET`. Register a Razorpay **test-mode** webhook at `https://<host>/api/webhooks/razorpay` for `payment.captured` and `payment.failed`. Keep the endpoint public to Razorpay, with TLS. The raw HMAC signature authenticates it. Configure automatic capture in the Razorpay test account; authorized-only payments do not enter review. A failed payment must leave the submitted cart and its items unchanged; Razorpay Checkout presents its normal payment retry within the modal using the same order.
3. Run `npm run worker` so P04 review deadlines and P03 notifications continue. Submit a mixed-category/multi-owner cart using current quotes and clean creative files. On `/cart`, check the full frozen total and pay once in Razorpay sandbox. Confirm one `payment_orders` row, one allocated `payment_captures` row, matching summed `payment_line_allocations`, no `booking_allocations`, and `booking_carts.paid_at` equal to the signed capture event time. The browser callback alone must leave a cart unfunded until the webhook arrives.
4. Sign in as AAL2 admin. Approve one line, reject another and let a third expire; verify only approval allocates inventory and both rejection paths create pending manual obligations. Fetch the gateway payment fee. Perform the rejected line refund in the Razorpay test dashboard; after the refund is `processed`, enter its `rfnd_...` ID, provider completion time and evidence on `/admin/refunds`. Select only the lines covered by that external transaction. Verify the completed transaction amount equals its allocations and the booking decision status did not change. Download the cart receipt and refund confirmation as the advertiser; another account must receive 404.
5. Fail a test payment in Razorpay Checkout and use its normal in-modal payment retry. Verify the Pixlwave cart, items, total and single Razorpay order are unchanged, and no funded review exists until a verified capture. Replay the signed webhook and deliver an authorized/failed event out of order; check that the captured payment, deadlines and allocations are unchanged. Withhold a capture webhook, then use **Check provider payments** on `/admin/refunds`; verify a durable missing-webhook alert appears while booking review stays unfunded. Redeliver the original signed event and verify the alert resolves. Test a late capture after checkout expiry or inside 192 hours of service: it remains captured money but the line is `payment_ineligible`, unreserved and in manual refund review. Investigate extra/mismatched captures in the admin exception queue; never auto-refund them.
6. Run `npm run lint`, `npm run typecheck`, `npm test`, `npm run test:docs`, `npm run build`, and `npm run check:client-secrets`. Record the revision, provider mode, capture/refund IDs, timings and screenshots or redacted reports in the P05 handoff. Sandbox account capabilities, webhook delivery, manual refund processing and client sign-off require a real operator; code tests alone cannot supply that evidence.

The sandbox implementation rejects production mode and live keys. Keep `P04_FIXTURE_FUNDING_ENABLED=false` outside disposable test databases. Never paste secrets, access tokens or payment method data into the handoff.
