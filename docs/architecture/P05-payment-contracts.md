# P05 payment contracts

Updated 2026-09-25. The application implementation is present; real sandbox and disposable-database acceptance remain unverified.

## Trust and timing

- `/api/payments/order` requires an authenticated cart owner, same-origin POST, a submitted unexpired cart and sandbox configuration. The database rechecks summed frozen lines and 192-hour notice before `payment_orders.cart_id` claims the one server-priced order. A provider timeout leaves the claim in `creating` for manual reconciliation; it never silently issues a second order. The provider receipt is `pw-` plus the cart UUID without dashes. The order uses INR, the frozen cart paise total and `partial_payment=false`.
- The browser opens Razorpay Checkout with the order ID and its normal in-checkout payment retry enabled. Payment failure leaves the Pixlwave cart and checkout unchanged. Its success callback only navigates to the booking page; it never funds a booking.
- `/api/webhooks/razorpay` verifies HMAC-SHA256 over the raw request body using `RAZORPAY_WEBHOOK_SECRET` and requires a provider event ID. Only `payment.captured` with a captured entity enters `record_razorpay_capture`. The signed event's `created_at` is the trusted capture timestamp used by P04; delivery time never resets the 168-hour review/cancellation or 192-hour notice clocks. Authorized and failed events have no effect on the Pixlwave cart or its normal checkout. A failed attempt is recorded for audit while the frozen items and same Razorpay order remain available. The capture webhook must be delivered or replayed with its original signed payload to preserve exact timing.
- `payment_captures.provider_payment_id` and `payment_webhook_events.provider_event_id` deduplicate callbacks. A different captured payment for an already funded cart, or a captured amount/currency mismatch, is recorded in `payment_exceptions` and shown to AAL2 admin. It never creates approvable lines. Unknown orders return a retryable server error until order attachment or investigation.
- The capture transaction inserts line allocations equal to the server-priced cart total, then calls P04 `record_trusted_cart_payment`. The whole transaction rolls back on an allocation failure, so Razorpay must retry. P04 records all trusted money; late checkout or insufficient 192-hour notice creates `payment_ineligible` lines and manual refund obligations. No payment code inserts capacity allocations or decides a booking. An AAL2 admin can fetch payments for an order using the provider API; a captured payment missing its signed event becomes a `payment_reconciliation_alerts` row and stays outside booking review until the original event arrives.

## Money and access

- Amounts are integer paise. Each captured cart line keeps its frozen paid value and `commission_bps=1500`. The 85/15 split is a policy snapshot for future verified fulfillment, not an earned owner payout at payment time. `payment_captures.provider_fee_paise` and line fee allocations use Razorpay's actual fee. Fee remainder paise are assigned in booking-line UUID order.
- Rejection and payment-ineligibility obligations subtract only allocated actual gateway processing charges. Cancellation retains its separate P04 5% all-inclusive fee. If Razorpay fee is not yet available, the admin completion path fetches it and updates pending obligations before any completed refund can be recorded.
- Admin completes refunds outside Pixlwave. `/admin/refunds` requires an AAL2 operator, verifies a `processed` Razorpay refund and captured payment with server credentials, then calls a service-only database function recording that operator and one external refund transaction whose selected obligations sum exactly to the provider amount. Duplicate references and allocations are rejected. The completed record emits `refund.completed`; the line remains rejected/cancelled. A grouped refund must refer to obligations in one cart/payment. Provider/bank credit timing is separate from this record.
- Authenticated cart owners may download their payment receipt and completed refund confirmation. Both routes recheck ownership and reconcile document line totals. These are HTML download records, not GST invoices. AAL2 admin reads the refund and exception queue; ordinary users cannot mutate finance tables, and direct admin RPC calls cannot bypass provider verification.

## Recovery

Inspect `payment_orders` stuck in `creating` against Razorpay test-mode Orders by receipt before manually attaching the exact matching order with the service-only `attach_cart_payment_order` RPC. Never create another order for that cart while the provider outcome is uncertain. On `/admin/refunds`, check provider payments for stale ready orders; captured payments with missing events become durable alerts. For a missing webhook, request replay/redelivery of the original signed `payment.captured` event. If an event is unavailable, keep captured money in manual reconciliation; do not reconstruct the capture timestamp from browser time or payment creation time. Investigate every `payment_exceptions` row and every pending `refund_obligations` row against provider records before external money movement. The app does not call Razorpay's refund creation API.

Verify the account's actual test-mode behavior during P05 acceptance.
